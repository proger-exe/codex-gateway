# codex-gateway idea

## Что это

`codex-gateway` это локальный HTTP-слой над установленным `codex` CLI. Его задача не заменить сам агент, а превратить его в стабильный внутренний сервис, к которому можно подключать другие клиенты:

- Telegram-бота;
- локальный CLI;
- веб-панель;
- автоматизации и cron-задачи;
- любые свои скрипты.

Идея в том, что агент остается "мозгом", а `gateway` становится нормальной точкой интеграции.

## Зачем нужен отдельный gateway

Если дергать `codex` напрямую из каждого клиента, быстро появляются проблемы:

- у каждого клиента своя логика сессий;
- сложно переиспользовать `thread_id`;
- неудобно централизованно ограничивать workspace и sandbox;
- structured output приходится изобретать заново в каждом месте;
- Telegram-бот, вебка и скрипты начинают дублировать одну и ту же glue-логику.

`codex-gateway` решает это как единый adapter layer:

- один способ разговаривать с агентом;
- одна модель сессий;
- один security perimeter;
- один механизм structured output;
- один контракт для будущих клиентов.

## Главная архитектурная идея

Слой делится на три роли.

### 1. Session runtime

Gateway управляет сессиями и знает:

- где рабочая директория;
- какая модель используется;
- какой sandbox разрешен;
- какой `thread_id` нужно продолжать.

Это делает агент пригодным не только для терминала, но и для API-вызовов из внешнего клиента.

### 2. Integration boundary

Все внешние клиенты общаются не с `codex` напрямую, а с HTTP API.

Это дает:

- единый wire contract;
- предсказуемые ошибки;
- возможность прикручивать новые клиенты без переписывания ядра;
- контроль безопасности на одном уровне.

### 3. Output normalization

Модель может свободно выполнять внутреннюю работу, но наружу gateway возвращает контролируемый результат:

- либо обычный текст;
- либо JSON по заранее зарегистрированной схеме.

То есть "мышление" и "интеграционный контракт" разведены.

## Почему тут есть schema registry

Structured output не хочется передавать как огромную схему в каждом `/chat` запросе. Поэтому схема регистрируется отдельно:

1. клиент загружает JSON Schema через `POST /schemas`;
2. получает `schema_id`;
3. передает `schema_id` в `/chat`.

Это дает несколько плюсов:

- короче запросы;
- одну и ту же схему можно переиспользовать;
- проще дебажить, какая именно структура ожидалась;
- будущим клиентам не надо таскать schema blob каждый раз.

## Почему `chat_context` идет отдельно

Не весь полезный контекст должен жить внутри session history.

Есть вещи, которые нужны только для конкретного вызова:

- стиль ответа;
- роль пользователя;
- формат для конкретного канала;
- дополнительные ограничения;
- локальные hints.

Для этого и нужен `chat_context`: это не новая сессия и не замена `message`, а дополнительный inline-контекст одного запроса.

Примерно так разделяются уровни:

- session = долгоживущий контекст разговора;
- message = текущая задача;
- chat_context = локальные условия именно этого вызова.

## Почему structured output делает именно gateway

Надеяться только на "модель послушается" недостаточно для нормальной интеграции.

Поэтому gateway берет на себя:

- wrapper prompt для structured режима;
- парсинг JSON;
- валидацию против сохраненной схемы;
- adaptive retry, если модель вернула невалидный ответ.

Это важно, потому что внешним клиентам нужен не "почти JSON", а надежный контракт.

## Adaptive retry

Retry тут не общий и не тупой.

Gateway различает тип сбоя:

- JSON вообще не распарсился;
- JSON распарсился, но не совпал со схемой;
- ответ пустой или мусорный.

И в зависимости от этого строит corrective prompt:

- если сломан JSON, просит вернуть только валидный JSON;
- если сломана схема, перечисляет конкретные проблемы;
- если ответ пустой, просит собрать объект заново.

То есть система не просто говорит модели "исправься", а направляет ее по причине ошибки.

## Почему контракт `/chat` сделан через единый `reply`

Снаружи клиенту удобнее один выходной payload, чем два параллельных поля.

Поэтому итоговая идея такая:

- `output_mode=raw` -> `reply` это строка;
- `output_mode=json` -> `reply` это JSON object или array.

Это проще для:

- Telegram-бота;
- веб-клиента;
- скриптов;
- typed SDK в будущем.

## Безопасность модели "myself only"

Этот gateway изначально спроектирован не как публичный SaaS, а как локальный приватный control plane:

- bind только на `127.0.0.1`;
- bearer token;
- allowlist по workspace;
- запрет `danger-full-access`;
- per-session lock, чтобы не ломать контекст параллельными запросами.

То есть это не "open API для всех", а локальный слой управления своим агентом.

## Куда это развивается дальше

Поверх такого слоя уже можно спокойно строить:

- Telegram-бота;
- web chat;
- MCP bridge;
- job runner;
- template-based automation;
- набор прикладных endpoints над `/chat`.

Именно в этом главная идея: сначала сделать хороший локальный gateway для агента, а уже потом подключать к нему любые интерфейсы.
